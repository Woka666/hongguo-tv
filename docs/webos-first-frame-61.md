# webOS 首帧停住调查：#61

反馈来自 LG OLED48 C1：经常卡在第一帧，重复刷新后可以播放。留言没有失败时的播放诊断，也未提供该 C1 安装包的版本号，因此不能将下面的复现直接当作该电视已确认的根因。

## 已复现的 HTTP 缺陷

`range-media.js` 的媒体响应写完所请求的字节后，只退出递归，没有调用 `ServerResponse.end()`。`Content-Length` 足以让客户端认为这一段收完，但 Node 仍将响应视为未完成。

在真实 HTTP 服务上限定复用同一条 TCP 连接：

1. 请求 `bytes=0-1`，客户端收到完整 206。
2. 同一连接请求下一段，服务端收到请求，但第二个响应被尚未结束的第一个响应挡住，直到测试超时。
3. 第一个响应没有触发 `finish`；provider 对应的在途读取保护也无法在该时刻释放。

该问题已分别用 `v0.2.120` 源码和公开 IPK 内的压缩模块复现。原测试显式设置 `Connection: close`，因此没有覆盖连接复用。电视先收到初始化/开头数据、再等不到后续媒体段时，可以表现为开头画面停住；是否对应这名用户的现场故障，仍需电视验证。

## 修正与回归

完成本次响应的全部字节后调用 `res.end()`，保留原有分块、背压、CENC、ETag 与 Range 校验。修正仅作用于 webOS 的 JS Range Service。

新增实际 HTTP 回归使用一个 keep-alive socket 连续发送六次请求，覆盖前缀探测、按需解密、HEAD、完整响应、大于两个输出块的背压及后续尾段读取；检查响应字节与六次 `finish`。同一回归在修正前因第二次请求阻塞而失败，修正后通过。

没有改成整集下载，也没有添加定时刷新、播放器重建或重新尝试的循环。该修正不涉及倍速声音或 Android/桌面播放器。

## 现场确认

该源码修正需下一次打包才会进入电视安装包。已发布的 `0.2.120-test.25` 含上述缺陷。

若更新后 C1 仍停住，应保留停止时的“播放诊断”：位置、缓冲秒数、readyState/networkState、暂停/定位状态、视频帧数、媒体 HTTP 状态与 Range/完整文件模式。它们用于区分后续网络停滞、暂停/定位以及平台解码问题；本次 HTTP 复现不等同于 LG 实机已修复。
